1. Git介绍

开源、分布式、直接记录快照、专针对数据

1.1 仓库概念

  1. 工作区：workspace，电脑能看到的目录，写代码的地方，通过git init创建的代码库，但不包括 .git文件(版本库)
  2. 暂存区/索引：Index/Stage，保存暂时信息，通过git add操作存入的地方(.git/index)，
  3. 本地库仓库：Repository，本地保存每个版本记录，本地文件夹 + Git 历史记录
  4. 版本库：工作区中的目录(.git，版本库=暂存区+本地库)
  5. 远程库：Remote，远程保存每个记录，托管在服务器上的代码库（如 GitHub/GitLab）

1.2 文件的三种状态

  1. 已修改（modified）：没进行add和commit操作，在工作区
  2. 已暂存（staged）：进行add操作，但没commit操作，保存到暂存区
  3. 已提交（committed）：进行add操作和commit操作，保存到本地库

1.3 配置

1. 配置文件

Git自带git config的工具控制Git外观和行为的配置变量（存储在三个不同的位置）

  1. /etc/gitconfig 文件：包含系统上每个用户及他们仓库的通用配置。 带有--system 选项时，会从此文件读写配置变量。
  2. ~/.gitconfig 或~/.config/git/config文件：只针对当前用户。 --global选项让 Git 读写此文件。
  3. .git/config：当前仓库的config 文件，针对该仓库。

每一个级别覆盖上一级别的配置，即 .git/config 的配置变量会覆盖 /etc/gitconfig 中的配置变量。

2. 配置用户信息(必要)

初次使用前配置用户名邮箱

当使用--globle参数时，所有仓库生效，只需要配置一次

3. 配置SSH

4. 文本编辑器(可选)

Git会使用操作系统默认的文本编辑器，也可指定

2.5 分支管理(branch)

版本控制中使用多分支同时推进多个任务，每个分支代表一条独立的开开发线

每个分支并行开发互不影响，对一个分支的增删改查不影响另一个分支，提高开发效率

永远从最新的 main 切分支，不要从别的旧分支或过时的 main 切，否则后面合并冲突会很多

  1. feature/xxx 、feat/xxx（— 新功能（开发新需求）

  2. bugfix/xxx 、fix/xxx— 修复 bug，开发环境 bug

  3. hotfix/xxx — 线上紧急 bug，需要马上上线修复

  4. release/v1.2.0 — 版本准备分支，打包测试、发版用

  5. docs/xxx — 只改文档、注释

  6. refactor/xxx — 重构代码，不改变功能

  7. test/xxx — 只加测试代码

若是想和其他开发人员合作，需要将数据放到共同的服务器上

GitHub项目的三个操作

  1. Watch/Unwatch:跟踪项目，每当项目发生变动时自己都会收到站内通知，或邮件通知
  2. Star：收藏、点赞，在个人信息列表的your stars目录里收藏着所有Star过的项目
  3. Fork：克隆、分支：相当于对原项目创建分支(包括历史记录)，自己克隆到本地修改后上传，可发起pull request给原项目作者，然后等待他的merge通知

3.2 连接远程库(remote)

3.3 远程main和并到本地main(fetch & merge)

  1. 方法 1：git pull（最简单，日常用）

执行完：本地 main 指针 = origin/main。

  1. 方法 2：先 fetch，再合并 origin/main
  1. 方法 3：reset（慎用！！）

强制让本地 main 指针直接对齐 origin/main

**注意一：**pull和rebase

rebase 不要在多人共用的公共分支上执行！ 只在自己本地的功能分支用 pull rebase；main/dev 这种公共共享分支，尽量用 merge，避免重写已经推送到远程的提交

如果默认git pull 没有配置成 rebase 模式（pull.rebase=false，这是默认），那么

git pull = git fetch + git merge

git pull --rebase = git fetch + git rebase

**注意二：**pull与fetch的拉取分支范围

git pull origin main 只会拉取 origin 的 main

git fetch origin 会拉所有远程分支

注意三：空格 origin main 和斜杠 origin/main

git fetch origin：更新本地库，但不更新工作区

origin main（空格）：两个参数，远程名 + 分支名

origin/main（斜杠）：一个名字，【远程追踪分支】ref

远程服务器上：分支叫 main

拉取到本地之后，本地存的远程镜像指针叫 origin/main

3.4 本地分支main

本地 main 的定位：尽量只是远程 origin/main 的镜像 / 副本，当做主干的本地镜像，不是用来开发、放半成品的地方。

origin/main（远程主干）一般约定：永远是随时可上线、稳定的代码。

本地 main不是单纯 “过渡中转站”，它是远程 main 在你电脑的镜像；你可以拿它做本地预合并测试，但是不承担正式合并上线的职责。正式合并交给 MR/PR。

  • 如果在本地 main 写新功能、提交 commit：
    1. 后续你执行 git pull / git merge origin/main 的时候，就容易产生多余 merge 提交；
    2. 一不小心手滑 git push origin main，就把未测试的代码直接推到远程主干，污染所有人的主干；
    3. 后续别人拉代码，拿到你还没上线的半成品。

  • 一般只是【本地预合并测试】，提前验证我的 feature 分支，合并到主干之后会不会冲突、能不能跑起来。 这时可以切到本地 main（先保证本地 main 已经同步 origin/main），然后 git merge feature/xxx，本地做一次合并，跑单元测试 / 本地启动项目，检查冲突和 bug。

  • 本地合并完，不要执行 git push origin main！，这个合并只是在你本机做验证。 真正把 feature 合入远程主干，走 PR/MR（合并请求），在 Gitlab/Gitee/Github 网页上操作。 网页 MR 才是正式流程：代码评审、流水线 CI 自动跑测试，通过后由平台帮你合并进远程origin/main。

  • 做完本地验证之后，你一般可以：

    • 删掉本地 main 上这个临时合并提交（或者直接放弃，不要推）；

    • 继续在 feature 分支改代码，提交 MR。

  • 尽量不随便动本地 main 分支，避免本地 main 被意外提交、产生脏数据。本地 main 只在需要的时候再 checkout 更新。例如以下两种方案通常采用版本B

3.5 指针管理

ref 是一堆命名引用（分支、tag、origin/xxx）；HEAD 是一个特殊 ref，用来标记「当前检出到工作区的是哪个提交」。

HEAD 属于 ref，但 ref 不都是 HEAD。ref 是大类，HEAD 是其中一员。

ref（如 refs/heads/main） HEAD
位置 在 .git/refs/ 下面 .git/HEAD，不在 refs 目录
作用 分支 / 标签 / 远程追踪的命名别名 标记当前工作区是哪个提交
数量 可以有成百上千个（很多分支 + tag） 仓库永远只有 1 个 HEAD
正常状态 存 commit SHA 存 ref: 某个ref
commit 时 ✅ 它会移动，更新成新 commit 哈希 ❗ HEAD 本身内容不变，跟着 ref
游离态 不会变成游离 可以直接存 SHA，进入 detached
  • ref（引用）

ref 就是带名字的指针，放在 refs/ 下面：

  • refs/heads/main（本地分支 main）
  • refs/remotes/origin/main（远程追踪分支 origin/main）
  • refs/tags/v1.0（标签）

特点： ✅ 名字固定，长期存在（除非手动删分支 /tag） ✅ 每个分支本身就是一个 ref； ✅ ref 可以被很多命令操作：checkout、merge、commit、push… ✅ 作用：给 commit 起别名，方便你用名字代替 SHA。

ref 文件在 .git/refs/xxx，内容：存 SHA，或者指向另一个 ref。

  • HEAD（.git/HEAD）

HEAD 是单独的特殊引用，不在 refs 目录里！ 路径：.git/HEAD，不属于 refs/\*。

HEAD 只有两种状态：

① 绑定分支（正常开发，最常见）

.git/HEAD 内容：

👉 HEAD 不直接存 commit 哈希，而是指向一个 ref（本地分支 ref）。

此时：HEAD → refs/heads/main → commit 哈希。

当你执行 git commit：

  1. 生成新 commit
  2. HEAD 指向的那个分支 ref（refs/heads/main）向前移动，更新成新 commit 哈希
  3. HEAD 本身内容不变，依旧写着 ref: refs/heads/main

重点：commit 不会移动 HEAD，移动的是分支 ref！HEAD 只是跟着 ref 走。

② 游离 HEAD（detached HEAD，检出某个 commit 哈希，不绑定任何本地分支）

比如：git checkout a34bc1（直接切 commit 哈希，不是切分支名） 这时 .git/HEAD 里面直接写 commit SHA，不再指向任何 ref

👉 HEAD 直接指向 commit，没有绑定任何分支 ref。

这个时候，你提交新 commit：HEAD 往前走，但没有任何 refs/heads/* 分支跟着走！ 一旦切回别的分支，这个新提交没有 ref 指向，之后会被 gc 回收（容易丢提交）。

4. 团队合作

4.1 团队内部合作

  1. 团队1创建项目，保存origin地址
  2. 团队2根据origin地址进行fork操作，然后克隆到本地仓库进行修改
  3. 修改好后从本地库上传到远程库，并发送pull request请求
  4. 团队1收到pull request通知，并决定是否接受merge
  5. 团队2等待merge通知

4.2 跨团队合作

  1. 团队 A（仓库维护方）
    1. 在 GitHub 新建公开或私有仓库，记录仓库 URL。
    2. 设定主分支保护、Issue/PR 模板、CI 规则。
    3. 定期查看 Pull Request，进行代码评审。
    4. 评审通过后执行合并，并在必要时打版本标签。
    5. 通知贡献方合并结果，关闭相关 Issue。
  2. 团队 B（功能贡献方）
    1. 在 GitHub 将团队 A 的仓库 Fork 到本组织或个人名下。
    2. 把 Fork 后的仓库克隆到本地开发环境。
    3. 创建功能分支，完成需求开发、测试与本地提交。
    4. 将功能分支推送到自己的远程仓库。
    5. 在 GitHub 发起 Pull Request，描述改动并关联 Issue。
    6. 根据团队 A 的评审意见迭代修改，直至合并完成。
    7. 合并后同步最新主分支到本地和远程，清理已完成功能分支。
  3. 系统管理员 / DevOps（可选支撑角色）
    1. 为仓库配置持续集成/持续部署（CI/CD）流程。
    2. 监控主分支健康状态，确保合并前通过全部检查。
    3. 在发布节点创建 Release 分支或 Tag，触发自动部署。
