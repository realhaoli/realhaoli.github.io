1、介绍

虚拟化技术主要用来解决高性能的物理硬件产能过剩和老的旧的硬件产能过低的重组重用

Docker项目的目标是实现轻量级的操作系统虚拟化解决方案，Docker的基础是Linux容器（LXC）等技术

Securely build，share and run any application，anywhere

打包：就是把你软件运行所需的依赖、第三方库、软件打包到一起，变成一个安装包

分发：你可以把你打包好的“安装包”上传到一个镜像仓库，其他人可以非常方便的获取和安装

部署：拿着“安装包”就可以一个命令运行起来你的应用，自动模拟出一摸一样的运行环境，不管是在 Windows/Mac/Linux。

Dockerfile：像自动化脚本，用来创建镜像

镜像/lmage：Docker将应用程序及其所需的依赖、函数库、环境、配置等文件打包在一起，称为镜像。

容器/Container：镜像中的应用程序运行后形成的进程就是容器，就像是面向对象程序设计中的类和对象一样，镜像是静态的定义，容器是镜像运行时的实体。只是Docker会给容器做隔离，又对外不可见。容器可以被创建、启动、停止、删除、暂停等。

2. 网络与端口

容器之间通信靠 Docker 网络，外部访问容器靠 -p 把端口映射到宿主机

参数 含义 示例
--network 指定容器连接的网络 --network mynet
-p, --publish 端口映射，格式：宿主机端口:容器端口 -p 8080:80，-p 10.0.0.1:8080:80
-P, --publish-all 将暴露端口随机映射到宿主机 -P
--expose 暴露端口但不映射到宿主机 --expose 8080
--dns 自定义 DNS 服务器 --dns 8.8.8.8
--dns-search 自定义 DNS 搜索域 --dns-search example.com
--add-host 添加主机名到 IP 的映射 --add-host db:192.168.1.100
--hostname 设置容器主机名 --hostname web01
--ip 在自定义网络中指定 IPv4 地址 --network mynet --ip 172.20.0.10
--link 连接另一个容器，已不推荐 --link db:db

Docker 网络是宿主机内核里的虚拟网络

  • bridge：默认网桥（docker0），容器之间可以互相访问，外部只能通过-p访问
  • host：不单独创建虚拟网卡，直接复用宿主机的网卡
  • none：容器禁用网络
  • overlay：跨主机容器通信,适用于集群环境

当创建容器不指定网桥（bridge0）或自定义bridge时，都会给容器分配一个IP地址（127.0.0.x），且不和主机127.0.0.x冲突，只有bridge内部各容器互相使用的时候采用容器的IP地址（127.0.0.x），否则外部程序访问容器只能-p指定

6、数据管理

6.1 数据挂载

当使用容器时，关于一些生产数据一般会遇到以下几个数据持久化问题：

不便于修改：当我们要修改容器内的内容时，需要进入容器内部修改，很不方便。

数据不可复用：在容器内的修改对外是不可见的。所有修改对新创建的容器是不可复用的。

升级维护困难：数据在容器内，如果要升级容器必然删除旧容器，所有数据都跟着删除了

两种解决办法：容器卷或宿主机目录挂载

**容器卷（Volume）**是在宿主机上抽象出来的卷，位置固定且由 Docker 管理，你通常不需要直接访问

能在创建卷时指定宿主机路径，也不建议直接修改该目录

-v 参数可以两种挂载

Docker 容器的挂载行为在内核层面是通过 mount(2) 系统调用在容器初始化时一次性完成的。挂载信息被固化在容器的挂载命名空间（Mount Namespace） 中，一旦容器启动，就没有安全的运行时接口去修改它

更换挂载的唯一正确路径是停止并删除旧容器，然后用新的挂载配置创建一个新容器

写法 类型 说明
-v /宿主机/绝对路径:/容器路径 绑定挂载 把宿主机目录/文件挂到容器
-v 卷名:/容器路径 卷挂载 把 Docker 卷挂到容器，卷不存在会自动创建
-v /容器路径 匿名卷 创建一个匿名卷挂到容器路径

6.2 数据卷

类型 特点与使用场景
命名卷 由 Docker 管理，推荐用于生产环境，支持数据持久化和容器间共享。
绑定挂载 将宿主机目录直接映射到容器，适合开发和调试，路径需绝对路径。
匿名卷 未指定名称的卷，由 Docker 自动创建，适合临时数据存储。

6.3 典型场景推荐

没有绝对的“哪个用得多”，取决于场景：

  • 生产环境：用 命名卷（named volume） 更多，因为由 Docker 管理，备份、迁移、跨平台都更方便。
  • 开发环境：用 绑定挂载（bind mount，挂载宿主机目录） 更多，因为需要实时修改代码、注入配置文件。
  • 临时数据：可能用 --tmpfs，数据不落盘。

Docker 官方建议：能用卷就用卷，除非你有明确理由必须直接使用宿主机目录。

维度 命名卷（docker volume + -v 卷名:路径） 绑定挂载（-v /宿主机/路径:容器路径）
谁管理 Docker 管理，存储在 /var/lib/docker/volumes/ 你管理，直接用宿主机目录
可移植性 高，与宿主机目录结构解耦 低，依赖宿主机具体路径
备份/迁移 容易，可打包卷或使用 docker volume 命令 需要手动备份宿主机目录
跨平台 Windows/Mac/Linux 表现一致 Mac/Windows 上可能较慢，权限问题多
权限控制 Docker 处理，通常更简单 容器内用户与宿主机文件权限容易冲突
开发热更新 不方便，修改代码后需重新构建或复制 非常方便，宿主机改完容器立即生效
配置文件注入 可以，但每次改配置要进卷操作 直接挂宿主机配置文件，修改即生效
性能 Linux 上很好，跨平台也好 Linux 上很好，Mac/Windows 上可能明显慢
生命周期 独立于容器，删容器不删卷 与宿主机目录绑定，容器删了目录还在

优先用命名卷

  • 数据库数据：MySQL、PostgreSQL、MongoDB 的数据目录。
  • 应用持久化数据：上传文件、日志、缓存。
  • 生产环境：需要稳定、可备份、可迁移。
  • 多容器共享数据：多个容器挂载同一个卷。

优先用绑定挂载

  • 开发时代码同步：把宿主机源码目录挂进容器，改完立即生效。
  • 注入配置文件：如 nginx.conf、.env、证书文件。
  • 使用宿主机工具处理数据：比如用宿主机上的编辑器、脚本直接操作文件。
  • 需要固定宿主机路径：某些 CI 或系统集成要求文件必须出现在特定位置。

用 --tmpfs 或匿名卷

  • 临时数据、敏感数据：不想落盘，用 --tmpfs /tmp。
  • 不需要持久化：匿名卷，但难以管理，不推荐生产使用。

选择建议（简单版）

  1. 生产持久化数据 → 命名卷。
  2. 开发代码/配置热更新 → 绑定挂载。
  3. 需要备份、迁移、跨平台 → 命名卷。
  4. 必须直接操作宿主机文件 → 绑定挂载。
  5. 临时内存数据 → --tmpfs。

7、Dockerfile

Dockerfile的本质是一个文件（构建镜像的说明书），通过指令描述构建镜像的过程，产物是：一个镜像。

Dockerfile 负责“怎么做一个镜像”，Docker Compose 负责“怎么把多个容器/服务组合起来运行”。

使用流程可以概括为：编写 Dockerfile → docker build 构建镜像 → docker run 运行容器、

“写 Dockerfile，build” 就是把你自己的应用代码，连同它需要的运行环境、依赖、启动命令，一起打包成一个可运行的 Docker 镜像。

对于编译型语言（Go、Java、Rust）或前端项目，通常会用多阶段构建

多阶段构建就是在一个 Dockerfile 里写多个 FROM，每个 FROM 开启一个独立的构建阶段。前面的阶段用来编译、打包，后面的阶段只复制运行真正需要的文件，最终镜像只包含最后一个阶段的内容。这样能大幅减小镜像体积，还能避免把源码、构建工具、开发依赖带到生产环境。

这样最终镜像里只有编译好的二进制文件和最小运行环境，不包含源码、编译器、构建工具，镜像更小更安全

也可简单用单阶段构建：只有一个 FROM，所有东西——源码、依赖、构建工具、运行环境——全都塞进同一个最终镜像里，比较臃肿。

8、Docker Compose

Docker Compose 是一个用于定义和运行多容器 Docker 应用的命令行工具，产物是：一组容器、网络、卷等运行环境。

核心是一个 docker-compose.yml 或 compose.yaml 文件，它描述了整个应用的服务、网络、卷等配置。通过指令定义集群中的每个容器如何运行。

YAML 最核心的语法规则：

  • 大小写敏感
  • 使用缩进表示层级关系
  • 缩进不允许使用 Tab，只允许空格
  • 缩进的空格数不重要，只要相同层级的元素左对齐即可
  • # 表示注释
  • : 号后面要加空格

Compose 使用的三个步骤：

  • 使用 Dockerfile 定义应用程序的环境或使用现成镜像。
  • 使用 docker-compose.yml 定义构成应用程序的服务，这样它们可以在隔离环境中一起运行。
  • 最后，执行 docker-compose up 命令来启动并运行整个应用程序。
维度 Dockerfile Docker Compose
作用 构建单个镜像 编排多个容器/服务
文件格式 Dockerfile 指令 YAML
阶段 构建阶段 运行/编排阶段
操作对象 镜像 容器、网络、卷、服务
常用命令 docker build docker compose up/down
能否定义多容器 不能 能
能否定义端口映射 只能 EXPOSE 声明，不实际映射 可以实际映射端口
能否定义网络和卷 不能，通常靠 docker run 参数 可以集中定义
是否依赖对方 不依赖 Compose 可以调用 Dockerfile，也可以不用
典型产物 镜像 一组运行中的容器

8.2 常用命令指令

命令 作用
docker compose up -d 核心命令。构建、（重新）创建、启动并后台运行所有服务。
docker compose down 停止并移除所有容器、网络。默认保留数据卷，加上 -v 可一并删除。
docker compose ps 列出当前项目的所有容器及其状态。
docker compose logs -f [服务名] 实时查看（指定服务的）日志。
docker compose exec [服务名] [命令] 在运行中的指定服务容器内执行命令，如 docker compose exec web sh 进入 shell。
docker compose build 仅构建（或重新构建）服务镜像，不启动。
docker compose stop / start / restart 停止 / 启动 / 重启服务，但不删除容器。
docker compose config 验证并查看 Compose 文件解析后的最终配置。

8.3 生产环境与最佳实践

当你的应用需要部署到生产环境时，可以参考以下实践：

  • 使用多个 Compose 文件：创建一个基础 compose.yaml 用于开发，再创建一个 compose.production.yaml 覆盖生产相关的配置（如移除代码绑定挂载、设置 restart: always 等）。启动时通过 -f 参数合并使用。

    bash

  • 善用 .env 文件：将密码、密钥等敏感信息放在 .env 文件中，用 ${VAR} 在 Compose 文件里引用，并将 .env 加入 .gitignore。

  • 管理启动顺序：depends_on 只能保证容器启动顺序，不能保证服务就绪。对于数据库等需要时间初始化的服务，应结合 healthcheck 和 depends_on 的 condition 使用，确保依赖的服务真正可用后再启动。

  • 配置日志轮转：为避免日志占满磁盘，可以为服务配置日志驱动和轮转策略。

生产环境更看重高可用、备份、监控、扩容、安全。很多公司会这样选：

组件 生产常见做法
自己的后端 打成 Docker 镜像，用 K8s 或云容器服务运行
MySQL 用云 RDS，不自己容器化
Redis 用云 Redis，不自己容器化
OSS 直接用阿里云 OSS / AWS S3，不是 Docker 容器
Nginx 可用云负载均衡，也可容器化
消息队列 用云 MQ，或自建容器
监控日志 用云监控，或自建 Prometheus/Grafana

关键点：像 OSS 这种是云服务，不是软件，你没法把“阿里云 OSS”装进 Docker。你只能在代码里通过 SDK 访问它。如果想自建对象存储，可以用 MinIO 容器替代。

配置信息可以写在 Docker Compose 里，但通常不会把敏感信息明文写进去。更常见的做法是：Compose 只写“引用”，真正的值放在 .env、CI/CD 变量、K8s Secret 或云密钥管理服务里

  1. 配置与代码分离：连接地址、账号密码不写死在代码里。
  2. 敏感信息不提交 Git：密码、AccessKey、SecretKey 绝不能进仓库。
  3. 环境变量优先：应用通过环境变量读取配置，不同环境注入不同值。
  4. 密钥交给专业服务：生产用云 Secrets Manager、K8s Secret、Vault 等。

生产环境：不靠 Compose 文件存配置

生产环境通常不用单机 Docker Compose，而是用 Kubernetes、云容器服务、ECS + CI/CD。配置来源更规范：

配置类型 常见存放位置
普通配置（地址、端口、Bucket 名） K8s ConfigMap、环境变量、配置中心
敏感配置（密码、AccessKey） K8s Secret、云 Secrets Manager、Vault
云 RDS / Redis 连接信息 云控制台创建后，写入 Secret 或配置中心
OSS / S3 访问凭证 IAM Role / RAM Role，避免写死 AccessKey

环境 普通配置 敏感配置 云负载均衡

生产 K8s ConfigMap Secret / 云 Secrets Manager 云控制台 / Ingress / Terraform
生产 ECS 环境变量 / 配置中心 云 Secrets Manager / RAM Role 云控制台 / Terraform
CI/CD Pipeline 变量 Pipeline Secret 不涉及

哪些适合 Docker，哪些不适合？

组件 适合 Docker 吗？ 说明
自己的应用 ✅ 非常适合 用 Dockerfile 打包，环境一致
Nginx ✅ 适合 官方镜像，挂配置文件即可
Redis ✅ 适合 开发、小规模生产可用
MySQL ⚠️ 可以但需谨慎 生产建议云 RDS，自己容器化要处理备份、高可用
OSS/S3 ❌ 不是容器 是云服务，直接用 SDK/API
MinIO ✅ 适合 自建对象存储，可容器化
Kafka/RabbitMQ ⚠️ 可以但复杂 生产常用云 MQ，自建需运维
Elasticsearch ⚠️ 可以但吃资源 生产常用云 ES
  1. 自己的代码 → 写 Dockerfile，构建镜像。
  2. 通用中间件 → 优先用官方镜像，不自己写 Dockerfile。
  3. 本地开发 → 用 Docker Compose 全部容器化，一键启动。
  4. 生产环境 → 应用容器化，数据库/缓存/对象存储优先用云托管，减少运维。
  5. OSS → 直接用云服务，不要试图装进 Docker。
  6. 单机小项目 → 可以全部用 Docker Compose 跑，包括 MySQL、Redis、Nginx。
  7. 大规模生产 → 用 Kubernetes + 云服务，而不是单机 Compose。
